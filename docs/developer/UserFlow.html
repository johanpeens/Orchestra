User Flow & Modals

Every screen, every dialog, and every route between them. Screen numbers match the files in Design/. The tables each step reads and writes are listed in Doc/DataModel.md.

1. How to read this

  • Full screen
  • Modal dialog
  • Decision
  • Saves to the database
  • Blocked or error

A modal is a dialog that floats on top of the page and blocks the rest of it until you either save or cancel. Every modal in this app has exactly two ways out: Save writes to the database and refreshes the page behind it, or Cancel throws the changes away and leaves the page untouched.

6. What happens when you press Save

Saving a step is the most involved write in the app - it touches four tables. Blazor Server means every one of these arrows is a SignalR round trip, so the whole thing runs inside a single database transaction and the Save button is disabled until it returns. 

sequenceDiagram
    autonumber
    actor U as User
    participant M as Add Step modal
    participant S as ProcessStepService
    participant V as Validator
    participant F as File storage
    participant DB as SQL Server

    U->>M: Fill in the form and press Save
    M->>M: Disable Save, show the spinner
    M->>S: CreateStepAsync(request)
    S->>V: Validate the request
    alt Something is wrong
        V-->>S: List of errors
        S-->>M: Failed result
        M-->>U: Red field messages, modal stays open
    else Everything checks out
        V-->>S: OK
        S->>DB: Begin transaction
        S->>DB: Next StepNumber for this process
        S->>DB: INSERT ProcessStep
        S->>DB: INSERT StepOwner per person
        opt A screenshot was attached
            S->>F: Save the file, get back a path
            F-->>S: StoredPath
            S->>DB: INSERT StepImage
        end
        S->>DB: INSERT ActivityLog
        S->>DB: Commit
        DB-->>S: Saved
        S-->>M: Success with the new step id
        M-->>U: Close, green snackbar, flow strip refreshed
    end

8. Rules every modal follows

These come from Frontend/TeamConventions.md and apply without exception.

  • Save and Submit sit on the left; Cancel and Close sit on the right.
  • Cancel never writes anything. Closing with the X behaves exactly like Cancel.
  • The Save button is disabled while the save is in flight, so a double-click cannot create two rows.
  • Validation errors keep the modal open and put the message under the offending field. A snackbar is not enough - the user cannot see which box is wrong.
  • Delete always opens a small confirm dialog first, and only ever soft-deletes.
  • After a successful save the modal closes, a green snackbar appears, and the page behind it reloads its data. The user should never have to refresh the browser.
